## 6. Strongest customer wedge and useful task

**Proposed buyer:** a small team building a research or developer assistant that sometimes needs a specialized paid-data endpoint during one task. **Proposed supplier:** a specialist API/report provider willing to expose a narrow, priced response to that assistant. Both are hypotheses, not customers or partners. The first realistic channel is direct developer/provider design partners already experimenting with Stellar, not selling a new general wallet to every consumer.

Preserve the original brief's concrete security-research example. A dependency-triage assistant is more intelligible than “buy useful APIs,” but AegisPay must not present fictional intelligence as an actual vulnerability assessment.

**Demo prompt proposal:** “Review the fictional `demo-parser` dependency for a release triage note. Get only the report needed for a basic advisory summary. Keep the total task spend within 0.10 Testnet XLM. If the available report cannot establish exploitability, say what is still unknown.” This is an example prompt to implement/rehearse, not an observed execution.

QuickSignal is the shallow fixture at **0.03 Testnet XLM / 300000 stroops**; DeepTrace is the richer fixture at **0.12 / 1200000**. Current seeded metadata actually describes fictional demo-parser dependency reports. A useful final answer would identify the report consulted, summarize only its supported findings, state its limits and cite the actual receipt. The report text must remain behind entitlement; public metadata should only describe it. The old 0.03 spike has no established quote/resource delivery and cannot be relabeled as a QuickSignal purchase retroactively.

There must be a reason to buy: the answer needs information absent from the free metadata and model context. If the prompt can be answered equally well without purchasing, the demo looks like an unnecessary crypto toll. Explicitly show the contribution of the purchased report to the final answer.

One affordable and one forbidden offer demonstrates a spending boundary; it is weak evidence of intelligent economic choice by itself. QA already calls for a changed-price rehearsal within permitted bounds and an unnecessary-data/no-purchase task. Those are the best additions for the 30% agentic criterion: genuine current-price tool calls, a concise stated rationale and a no-spend outcome when paid data adds no value. Do not force QuickSignal in code or show private reasoning. A changed-price scenario must use actual trusted catalog/quote values and later authorized tests; this assessment changes none.

**Demand test:** ask developers to show the last task blocked by a new paid API, what they actually did, and what integration or recovery cost they incurred. Ask a provider for permission to integrate one real endpoint. A usable repeat run and a provider/developer commitment are stronger signals than “cool project” feedback. Prepaid API keys, ordinary usage billing and conventional idempotent payments may remain better choices for many teams.
