## Findings

### R1 — P1 / high: refreshing wallet state clears an operator spending suspension

**Evidence:** `src/server/http/application.ts:145` reads an agent, then `:147` awaits live wallet/policy reads; `:151` writes `status: policy ? 'active' : ...` without preserving `disabled` or checking the current status. `src/server/domain/wallet.ts:169` performs the same unconditional promotion when confirming a wallet operation. The `disabled` state is explicitly present in `src/server/db/schema.ts:40` and the data model. New-run and quote-acceptance readiness deliberately require `active` at `src/server/domain/purchases.ts:32`, `:53`, and `:100`. PRD's operating narrative (`docs/prd.md:75`) and incident handling (`docs/security-compliance.md:64`) require recovery/revocation to remain available while new purchasing is disabled.

**Trigger and effect:** an operator sets the agent to `disabled` while its on-chain policy remains valid, then an authenticated owner refreshes `GET /api/v1/wallet-state`. The refresh writes `active`, removing the application suspension; a later run/acceptance can pass readiness again. The same loss occurs if an operator disables the agent while an already-started wallet observation or refresh is awaiting RPC. This is a concrete overwrite in the current code, conditional on use of the existing disabled state; no suspension or subsequent live spend was performed during review. It affects the spending-control boundary associated with INV-007. It does not bypass the on-chain cap or prove a duplicate financial handoff.

**Narrow fix:** refresh chain-derived policy fields without changing the operator's disabled decision. Preserve it using the current locked row or an atomic SQL conditional in both update paths, so checking only the earlier JavaScript snapshot cannot lose a concurrent disable. Re-enabling should be an explicit operator action; identity-only recovery and safe wallet operations must remain possible.

**Missing verification:** add PostgreSQL cases for disabled → wallet-state refresh and disabled → wallet confirmation, plus a second-connection disable during the awaited chain read. Assert the row remains disabled and both fresh run creation and quote acceptance remain refused while existing recovery still works. Current wallet/HTTP tests do not cover these transitions. Sent to the coordinator promptly as Orca message `msg_03138b71894f`.

The attempt is withheld and its budget remains held, which is safe, but operators receive the same generic status as an unavailable RPC. Repeated observation does not expose that human review is needed. **Narrow fix:** distinguish an explicit allowlist of deterministic identity/invocation/evidence contradictions from transport unavailability or temporarily missing chain/event data. Lease-fence a `manual_review` transition with a fixed safe reason. Keep the original identity, reservation and observation-only boundary; neither release funds nor create a replacement attempt. ### R3 — P2 / medium: the final deadline check precedes additional awaited work before first dispatch

**Evidence:** `apps/server/src/worker/payment.ts:112` commits the handoff marker, and `:114` checks quote expiry. It then awaits another `paymentSnapshot` at `:115` and `assertWorkerFence` at `:116` before calling `gas.submit` at `:117`. The fence checks only lease ownership/lease expiry (`src/server/domain/purchases.ts:18`–`:19`), not quote freshness. Once the marker is timely, later evidence acceptance checks marker time rather than dispatch time (`src/server/domain/evidence.ts:37`–`:39`). The design explicitly distinguishes late confirmation after timely dispatch from anomalous post-deadline dispatch (`docs/system-design.md:78`).

**Trigger and effect:** the quote is still valid at `:114`, but a slow pool/database read at `:115` or the fence's DB-time read spans the remaining quote lifetime while the 120-second agent lease is still valid. The worker proceeds with its first network submission after quote expiry. A successful chain execution may subsequently be granted using the earlier marker. This is a concrete ordering gap, not an observed event in the real attempt. Its impact is stale first dispatch and incorrect handling of that anomaly; it does not create a second submit.

**Narrow fix:** place the final conservative deadline decision after the final awaited ownership read and immediately before dispatch, with no additional application awaits in between. Preserve the irreversible marker and held budget if the deadline has elapsed after marker commitment; record a fixed anomaly/manual-review reason instead of releasing, resigning or redispatching. Use the existing DB-time convention and account conservatively for elapsed time around the final read. This cannot guarantee remote inclusion before expiry, nor should it reject ordinary late confirmation after a valid first dispatch.

**Missing verification:** delay the post-marker snapshot/fence read across quote expiry while preserving a valid agent lease, then assert zero submit calls, unchanged handoff identity/held budget and no entitlement. Existing expiry coverage delays `after_envelope` (`tests/integration/payment-recovery.test.ts:82`) or `after_submit` (`:88`); it does not exercise the awaited operations between the last deadline check and submit.

## Operational limits and lower-priority observations

- **Receipt-key rotation fails closed but invalidates active recovery.** `merchant/receipts.ts:11`–`:18` has a single current HMAC key and no persisted key version. Both metadata (`:34`) and content (`:44`–`:45`) first require the current derivation to match the immutable stored hash. Changing the key prevents even an otherwise valid old supplied token from working. This does not leak a report and seamless rotation is not an explicit MVP acceptance requirement. Keep web/worker key configuration aligned and stable during active windows; a future rotation feature should retain versioned verification keys through expiry and test recovery without extending the window. Do not rewrite historical receipt hashes to conceal the mismatch.
- **Owner state includes internal lease metadata.** `http/application.ts:51` selects the complete agent row and `:56` serializes it, including lease owner/deadline from `db/schema.ts:38`. Those fields are unnecessary for the owner read model. No current route accepts that lease token as authority, and no signing secret/ciphertext is in this row, so this is low-priority field-minimization rather than a demonstrated authorization exploit. Select the documented safe columns explicitly and add an owner-state response assertion.
- **Crash-test wording needs its execution limit.** The new exception hooks exercise sequencing and connection competition but run catch/finally; they do not prove OS-process death durability. `tests/integration/payment-recovery.test.ts:45` throws in-process, while `payment.ts:155` releases the lease in finally. The 120-second agent lease also consumes essentially the whole 120-second quote lifetime after a real pre-handoff process death; conservative expiry is expected unless lease/restart behavior is changed and verified. Broader process-kill tests are already declared as TASK-006 work, not a hidden pass here.
- **No broader release claim.** I inspected what the tests assert, without rerunning them. Recorded PostgreSQL/unit/spike pass counts remain the writer's historical run evidence. This review supplies no actual paid success, deployed authenticated purchase, real model loop, Freighter consent, two-distinct-purchase acceptance, comprehensive client-bundle scan or hosted cold-start proof.
